## 为什么主摄也走 AI

日志 1980 行：双广角辅助相机被拒绝，原因 `exactPrimaryLockUnsupported`。
日志 1984 行：改为独立主摄，`physicalInput=true, depth=false`。
日志 2008 行：`appleFallbackReason=native depth unavailable`，实际 `computational`。

代码对应：

- `CameraManager.swift:693` 仅在 iOS 27 及以上检查精确主镜头锁定能力；更早系统返回不支持。
- `MainCameraCapturePolicy.swift:58` 拒绝不能精确锁定的非 LiDAR 辅助相机。
- `CameraManager.swift:529` 配置阶段也要求 iOS 27 的精确锁定接口。这台设备日志中没有可用的其他辅助输入。
- `DepthPhotoProcessor.swift:375` 没有可用原生深度时调用离线模型。

这是当前应用为保证 RGB 来自所选镜头而采用的限制，不能解释为 iPhone 或系统本身完全不支持原生景深。兼容策略需要在保住所选镜头身份的前提下重新评估。

## 首次加载证据与持续慢的边界

模型在 `MonocularDepthEstimator.swift:37` 拍后才加载；`loadModel` 在 52 行复用缓存，72 行保存模型。相机页面持有的处理器持续复用，所以代码没有主动要求每拍一张都重新加载模型。

本机 Apple M5 临时基准使用当前源码副本加计时、12MP 合成图：模型首次加载加推理分别观察到 18.021 秒和 6.877 秒，随后两次约 0.033–0.059 秒。此数据只能支持冷/热启动差异，不能替代 iPhone 耗时。固定深度、不运行模型的完整合成处理热运行约 0.38–0.87 秒。测试输出位于 `/tmp/testcamer-perf-20260923/release.log` 和 `debug.log`。两组按顺序运行、系统缓存状态不同，不用来比较 Debug 与 Release 的总体性能。

当前设备日志只有两张带新算法标志的计算景深拍摄，分别属于两个独立进程的第一张，没有同一进程第二、第三张拍摄记录。因此已经定位两次约 8 秒慢拍的主要区间，但还不能证明或解释“连续每张都约 8 秒”。相册导入和编辑事件不计为后续拍摄。

日志 revision/build 没有 Git SHA，无法严格确认安装包对应哪个提交；新算法标志和相册导入行为与当前代码相符。

## 每张都会累加的工作

`ViewController.swift:319–333` 先等待相机完成，再等待完整处理才显示成片。计算路径在返回前依次完成虚化、完整分辨率输出、像素变化检查、诊断图、全尺寸 JPEG、效果预览和原图预览。显示之后再于 340 行等待本机保存，342 行打开编辑器，整个 Task 结束才停止 spinner。

人物实例选择在 `DepthPhotoProcessor.swift:397` 每张执行；命中人物还会进一步做人脸和高精度分割。但当前两张慢拍的人物选择只有 21–34 毫秒，不是主要瓶颈。本机保存发生在结果显示日志之后，也不是上述 6.3 秒的来源。

45 秒常量是相机回调超时保护，没有正常路径固定等待。后台处理不等于用户无需等待：当前界面必须等整个结果准备完成。

## 建议处理顺序

1. 拆开记录模型加载、输入转换、推理、深度转换和完整处理耗时；同一进程连续拍摄至少三张，核对持续慢区间。
2. 评估 iOS 26 主摄原生深度的兼容路径，保留所选镜头身份验证，避免长期不必要地回退模型。
3. 对确实需要模型的镜头提前加载/预热，保持实例复用，移出首次快门等待链。
4. 将诊断图按需生成，考虑先显示可编辑预览，再完成全尺寸输出，减少每张必须等待的非核心处理。

## 官方 API 复核：iOS 26.4 可以走原生景深（补充）

根据苹果官方文档和本机 Xcode SDK 声明，原生深度拍摄并不要求 iOS 27：

| 能力 | API | SDK 声明最低 iOS |
|---|---|---:|
| 照片附带原生深度 | AVCapturePhotoOutput / AVCapturePhotoSettings.isDepthDataDeliveryEnabled | 11.0 |
| 苹果景深渲染 | CIContext.depthBlurEffectFilter(forImageData:options:) | 12.0 |
| 锁住当前活动的主镜头 | setPrimaryConstituentDeviceSwitchingBehavior(.locked, restrictedSwitchingBehaviorConditions: []) | 15.0 |
| 指定某颗子镜头并锁定 | setPrimaryConstituentDeviceSwitchingBehaviorLockedWith(_:) | 27.0 |

官方流程：选择支持深度的组合相机输入，加入 session / photo output 后检查 isDepthDataDeliverySupported，运行 session 前启用 output 的深度交付，每次拍照在 settings 上请求深度，回调读取 photo.depthData 或保留带附件的原始容器。该接口交付 RGB 与深度；可见虚化由后续景深滤镜完成。硬件、格式和变焦仍需逐项检查，不能只根据系统版本宣称实际交付一定成功。

当前 CameraManager.swift:693–695 在 iOS 27 以下将 supportsExactLock 固定为 false，MainCameraCapturePolicy.swift:58 因此直接排除非 LiDAR 组合相机。这是项目额外限制，不是系统原生深度 API 的版本限制。故优化应优先恢复 iOS 26 的原生兼容路径，而不只预热 AI 模型。

保住所选主摄身份的兼容方案：让组合相机开始运行，读取 activePrimaryConstituent，确认其确为用户选择的物理主摄，再用 iOS 15 的 .locked 锁住当前镜头并重新核对锁定状态、变焦和深度支持。旧 .locked 不能指定另一颗镜头；不能把设置某个 zoom 等同于镜头已切换成功，运行前 activePrimaryConstituent 也可能为 nil。该兼容方案尚未在本次排查中实现或完成真机验收。
